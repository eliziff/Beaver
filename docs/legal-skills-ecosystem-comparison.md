# Legal skill and plugin ecosystems compared to Mike

Status: research complete against the public ecosystem and the working tree on
2026-07-27. No production code was changed.

## Scope and decision rule

This report surveys the public "legal agent skill" ecosystem — Lawve AI,
`lawve-ai/awesome-legal-skills`, and `anthropics/claude-for-legal` — and
compares it to Mike's built-in workflow surface. It then answers three
questions:

1. which published workflows are strong and generic enough to ship as Mike
   defaults;
2. which recurring categories of "skill" are really deterministic code wearing
   a `SKILL.md` costume; and
3. what Mike should build instead.

The rigour test is the one already adopted in
[Deterministic and durable work](deterministic-durable-work-audit.md): a
**strict win** removes a model round trip, reduces model-visible text, makes
verified state survive a restart, or deletes a duplicate implementation. A
capability only deserves to stay a prompt if it is **Class D** under
[the Word actions catalog](deterministic-word-actions-catalog.md) — the desired
semantic result cannot be inferred safely from text or formatting alone.

## The ecosystem

| Tier | What it is | Scale |
| --- | --- | --- |
| Lawve AI | Community marketplace of `SKILL.md` files plus MCP connectors, security-audited before listing, provider-neutral across Claude/ChatGPT/Gemini. Distributed as an Anthropic connector. | ~139 skills in `awesome-legal-skills` |
| `anthropics/claude-for-legal` | 12 vertical plugins (commercial, corporate, employment, privacy, product, regulatory, AI governance, IP, litigation, clinic, law-student, builder-hub). Each is skills + slash commands + hooks + `.mcp.json` + scheduled managed agents, anchored by a `CLAUDE.md` practice profile written by a cold-start interview. | ~100 skills, 25+ connectors, 12 cron agents |
| Point tools behind the skills | Definely, SuperDoc, CoCounsel/Westlaw, Trellis, CourtListener, Everlaw, iManage exposed as MCP endpoints. | — |

Three structural observations matter more than the counts.

**The unit of distribution is prose.** A skill is a markdown file with
frontmatter. It cannot be diffed for behavioural change, cannot be unit tested,
and carries no assertion about which version of a rule it encodes.

**The quality mechanism is a security audit, not a correctness audit.** Lawve
screens for malware, prompt injection, hidden instructions, credential
exposure, and exfiltration. Nothing in either ecosystem checks whether a skill
computes the right deadline.

**Citation integrity is an honor system.** `claude-for-legal` instructs users
to connect a research connector first, and flags model-recalled citations
`[verify]`. Skills such as `source-locked-verification-larissa-meredith-flister`
and `mandatory-verification-larissa-meredith-flister` exist purely to restate
that instruction more forcefully. This is prompt discipline standing in for a
transport guarantee.

## Mike's current position

Mike ships **24 built-in workflows** in
`backend/src/lib/systemWorkflows.ts`, generated by `scripts/build-workflows.js`
from the `mike-workflows` collection: 13 `assistant` and 11 `tabular`.

| Dimension | Current value |
| --- | --- |
| Practice areas | Corporate, Finance, Real Estate, Employment, Private Equity, General Transactions, Litigation (one workflow) |
| Jurisdictions | `["General"]` on every workflow |
| Language | English on every workflow |
| Shape | `metadata + skill_md + columns_config` |

The workflow record is structurally the same object as a `SKILL.md`:
frontmatter-equivalent metadata plus a markdown body. Import and export cost is
therefore near zero, and `backend/src/routes/workflows.ts` already persists
user-authored `skill_md`. Compatibility is not the constraint.

### Where Mike leads

- **Verified evidence rather than asserted citation.** Opaque handles
  (`mike-evidence:v1:<sha256>`, `mike-provider-evidence:v1:<sha256>`) in
  `backend/src/lib/docxEvidenceCitations.ts`, server-verified quote spans and
  native anchors in `backend/src/lib/legalSourceLinks.ts`. An unverifiable
  citation is structurally difficult to emit rather than discouraged by prompt.
- **Deterministic Word operations.** `library_link_docx_citations`,
  `library_fix_docx_supras` (real `NOTEREF \h` fields), tracked-change
  application in `backend/src/lib/docxTrackedChanges.ts`, and the Table of
  Authorities pipeline. The public catalog answers the same need with seven
  separate `docx-processing-*` skills that each re-teach a model to drive a CLI.
- **Local authoritative corpora.** A2AJ and CourtListener bulk data plus the
  universal legal PDF engine, offline and account-free.
- **An existing doctrine.** The deterministic/durable audit and the Word actions
  catalog already encode the exact decision rule this report applies.

### Where Mike is behind

- No coverage of privacy, AI governance, IP, regulatory, or legal operations.
- One litigation workflow (`builtin-e-discovery-tabular-review`) and no
  litigation drafting or procedure.
- No jurisdiction dimension in practice, despite the metadata field existing.
- No practice-profile substrate — nothing equivalent to `CLAUDE.md` capturing a
  firm's playbook, house conventions, escalation rules, or risk calibration.
- No scheduled or headless execution.
- No skill import, provenance, or trust layer.

## Pattern: what is fake in the published catalogs

Sorting the combined ~240 published skills against the Class A–D test, six
clusters are deterministic computation expressed as prose.

### 1. Date and deadline arithmetic

Examples: `litigation-deadline-calendar-dave-marcus`, `leave-tracker`
(FMLA/CFRA/PFL/ADA), DSAR statutory clocks, `renewal-watcher`,
`ip-renewal-watcher`, `entity-compliance` filing deadlines, NPRM comment
windows.

This is a rule table, a court-holiday calendar, and service-method extensions.
Language models are unreliable at multi-step date arithmetic and, more
importantly, produce no artifact a supervising lawyer can check. This is the
highest-liability category in the catalog and the one most obviously misplaced.

### 2. Statutory decision trees

Examples: **five** separate EU AI Act classification skills
(`eu-ai-act-classification-*`, `eu-ai-act-roles-*`, `eu-ai-act-triage-*`), NIS2
scope, Article 27 FRIA triggers, Article 35 DPIA triggers, ABC worker
classification, Indian foreign-investment approval.

These are published, closed decision graphs over a small number of typed facts.
The genuine model work is extracting facts from prose into the form. Walking
the tree is not model work, and five prompt reimplementations of one statutory
graph is exactly the duplicate-implementation smell the audit rule names.

### 3. List screening

Examples: `sanctions-screening-gillan-saleh`,
`new-designation-screening-test-amir-fadavi`,
`screening-alert-adjudication-amir-fadavi`, trademark knockout in
`ip-legal:clearance`.

Name matching against an authoritative designation list is fuzzy string
matching plus a list-freshness date. The lists are downloadable. Asking a model
to recall whether a party is designated is not a shortcut, it is a defect.

### 4. Document mechanics

Examples: seven `*-processing-*` skills, `legal-document-drafting-formatting`,
formatting-preserving translation, "render the result as `.xlsx`".

Class A and B under the Word actions catalog, and largely settled inside Mike
already.

### 5. Citation hygiene as prompt discipline

Examples: `source-locked-verification`, `mandatory-verification`, the
fact-checking half of `red-team-verifier-patrick-munro`, and the `[verify]`
convention across `claude-for-legal`.

Mike solves this at the transport layer with evidence handles. A prompt cannot.

### 6. Matter and project-management scaffolding

The 23 `scott-margetts` legal-operations skills. `invoice-review-compliance`
against billing guidelines and LEDES codes is a rule engine plus arithmetic;
`timeline-generator` is critical-path method. These describe a project
management product, not a reasoning task.

### Mike is not exempt

`builtin-commercial-lease-review` instructs the model to "flag general drafting
errors that may affect the represented party, including inconsistent defined
terms, inconsistent entity names, cross-reference errors, numbering issues,
duplicated provisions, missing schedules, and internal inconsistencies."

That is a lint, not a judgment. It belongs in deterministic code beside
`backend/src/lib/docxDeterministicCleanup.ts`, and its results belong in the
review table as verified findings rather than as model recall.

## Workflows worth adopting as Mike defaults

Adoption criteria: generic across jurisdictions, not already covered by the 24
built-ins, and Class D.

| Candidate | Source | Why it fits |
| --- | --- | --- |
| Amendment history / consolidated effect | `commercial-legal:amendment-history` | Resolving what a clause says after a chain of amendments; fills a real transactional gap |
| Diligence issue extraction | `corporate-legal:diligence-issue-extraction` | Materiality-graded issues; upgrade path for existing tabular reviews |
| Material contract schedule | `corporate-legal:material-contract-schedule` | Disclosure-schedule generation from a document set |
| Privilege log review | `litigation-legal:privilege-log-review` | First-pass review with flags; Mike's evidence layer makes it defensible |
| Subpoena triage | `litigation-legal:subpoena-triage` | Scope, burden, privilege, plan |
| Claim / element chart | `litigation-legal:claim-chart` | Element-by-element mapping to record evidence |
| Deposition preparation | `litigation-legal:deposition-prep` | Outline tied to case theory |
| Matter intake | `litigation-legal:matter-intake` | Structured intake with issue spotting |
| Open-source licence review | `ip-legal:oss-review` | Deployment-model-dependent; genuinely analytic |

Do not adopt as defaults: anything in clusters 1–3 above (build it as code);
jurisdiction-locked skills (the six Icelandic skills, the French tribunal
writs, Connecticut divorce) which are good marketplace items and bad defaults;
and the legal-operations suite, which is a separate product.

## Three proposed workflows that pass the rigour check

Each is Class D, generic across jurisdiction and practice, has no deterministic
implementation, and exercises capability Mike already owns.

### 1. Adversarial review — `builtin-adversarial-review`

Takes any Mike artifact — a review table, a draft, a memo, a brief section —
and attacks it from opposing counsel's and a skeptical bench's position: the
weakest link in the reasoning chain, the strongest available counter-argument,
and which facts are assumed rather than evidenced.

**Why it passes.** Constructing the best available counter-argument is
generative reasoning over legal and commercial world knowledge. There is no
deterministic detector for "this argument is weak," and no fixture set could
enumerate the counter-arguments in advance.

**Mike leverage.** Every asserted weakness must carry an evidence handle or be
explicitly marked unsupported, which converts the ecosystem's
`red-team-verifier` prompt-hope into an enforced output contract. Fills the
litigation gap without taking a jurisdictional position.

**Related public skills.** `opposing-counsel-review-larissa-meredith-flister`,
`judicial-first-impression-larissa-meredith-flister`,
`red-team-verifier-patrick-munro`.

### 2. Playbook deviation review — `builtin-playbook-deviation-review`

The user supplies a playbook, standard-form set, or prior precedents. The
workflow classifies each material clause against it and reports the deviation
together with its commercial materiality.

**Why it passes.** The hard part is semantic equivalence across paraphrase.
"Aggregate liability shall not exceed the fees paid in the twelve months
preceding the claim" and "capped at TTM fees" are the same negotiating
position; no diff, regex, or clause classifier sees that. Materiality is
contextual judgment about the deal, not a property of the text.

**Mike leverage and cost.** This is the single highest-volume real legal-AI
task, and `builtin-nda-review` currently has no playbook concept at all. It
requires adding a practice-profile substrate — Mike's answer to `CLAUDE.md` —
which is a prerequisite worth paying for on its own.

**Related public skills.** `contract-review-anthropic`, `nda-triage-anthropic`,
`nda-review-jamie-tso`, `commercial-legal:review`.

### 3. Chronology and disputed-fact builder — `builtin-chronology`

From a document set, produce a chronology in which every event carries an
evidence handle and a status: corroborated, single-source, or contradicted,
naming the conflicting sources.

**Why it passes.** Cross-document entity and event resolution — recognising
that "the Buyer," "Purchaser," and "Acme SPV II" are one party across four
document types — and detecting that two sources assert incompatible facts are
both semantic. Deterministic code owns the mechanical half: date normalisation,
ordering, de-duplication, and citation construction.

**Mike leverage.** This exercises the pinpoint evidence stack harder than any
current workflow and fills the litigation and e-discovery gap where Mike has
one entry.

**Related public skills.** `litigation-legal:chronology`,
`mediation-dispute-analysis-jinzhe-tan`.

## Proposed feature: a legal rule pack engine

One feature subsumes roughly 40 of the published skills, including every skill
in clusters 1–3 above, plus `leave-tracker`, `docket-watcher`,
`renewal-watcher`, `entity-compliance`, DSAR clocks, IP renewals, and all five
EU AI Act classification skills.

A **rule pack** is a versioned, jurisdiction-scoped, declarative artifact that
Mike executes as code rather than as a prompt.

```yaml
rulepack: on-rules-of-civil-procedure/service-deadlines
version: 2026.1
jurisdiction: CA-ON
source:
  provider: a2aj
  source_id: <stable source id>
  revision: <source revision or content sha256>
calendar: courts/CA-ON/holidays.2026.json
inputs:
  - { name: trigger_event, type: date }
  - { name: service_method, type: enum, values: [personal, mail, email, courier] }
  - { name: document_type, type: enum, values: [statement_of_defence, motion_record] }
rules:
  - id: r3.01-1-b
    when: service_method == "mail"
    add: { days: 5, count: calendar }
    cite: { block_id: "r3.01(1)(b)" }
```

### The split

| Layer | Owner | Rationale |
| --- | --- | --- |
| Extract facts from prose into typed inputs | Model | Genuinely semantic; unstructured input |
| Evaluate rules, compute dates, walk the decision tree | **Code** | Auditable, testable, zero tokens, deterministic |
| Cite the rule text that produced the result | **Code** | Mike already has legislation corpora and evidence handles |
| Explain the result in prose | Model | Downstream of a fixed answer; cannot change it |

### Why it beats the skill-file version

**Correct.** Date arithmetic and statutory threshold tests stop being sampled
from a distribution.

**Auditable.** The output is a receipt — inputs, rule IDs fired, result,
citation to the rule text — that a supervising lawyer can check in seconds. A
skill file's narrated reasoning is not evidence of anything.

**Free and instant.** Zero model round trips for the computation itself. This
is a strict win under the audit rule on all four counts.

**Versioned and invalidatable.** Key results on
`rulepack_id + version + source_revision + calendar_hash`, following the
artifact-keying discipline in finding 1 of the deterministic audit. When a
court amends a rule, every prior calculation becomes knowably stale. A skill
file written in 2025 rots silently.

**Abstains rather than guesses.** Following the routing doctrine in finding 5,
ambiguous or unmapped inputs return candidates plus an explicit "cannot
compute," never a forced answer. In a malpractice-adjacent domain this is the
property that makes shipping defensible.

**Correctly extensible.** A rule pack is the right unit for community
contribution: data, with a source citation and a fixture set, that can be
diffed, reviewed, and tested. Prose skills can be none of those things.

### Equivalence gate

Before any pack ships:

| Measure | Required result |
| --- | --- |
| Published-example fixtures | Every worked example in the source rule or statute reproduces exactly |
| Adversarial negatives | Ambiguous, out-of-scope, and undated inputs abstain rather than answer |
| Source binding | Every result cites a resolvable block in the versioned source |
| Staleness | A source-revision or calendar change invalidates cached results |
| Model calls | Zero for evaluation once inputs are typed |

### Explicitly not in scope

Consistent with the audit's "do not build yet" list: no model-based rule
router, no LLM fallback that invents a deadline when a pack abstains, and no
second legislation parser. A missing rule pack is a missing rule pack.

## Cheaper runner-up: contract structural lint

Not the headline proposal, but the highest ratio of value to effort available:
defined terms declared but unused, used but undefined, or inconsistently
capitalised; broken internal cross-references; numbering discontinuities;
inconsistent party names; dangling schedule and exhibit references; conflicting
liability caps.

This subsumes `lawyerscrib-garry-haas`, `legal-design-assessment`, part of
`builtin-proofread`, and the drafting-errors paragraph of every review workflow
including Mike's own lease review. It costs zero tokens, extends
`docxDeterministicCleanup.ts`, and its findings can be injected into review
tables as verified rather than recalled.
